# staged-commit

Turn a dirty working tree into a series of small, self-contained commits. One commit = one logical change. The user stays in control: you propose the grouping and messages, then commit (or hand back for the user to run), and you never push without being asked.

## When to invoke

- "commit this" / "commit my changes" / "commit for me"
- "commit in stages" / "break this into commits" / "stage and commit"
- "wrap these edits into commits"

Do **not** invoke to push, open a PR, or amend already-published commits unless explicitly asked.

## Hard rules (never violate)

1. **No AI/tool references in messages.** Never write "Copilot", "Claude", "AI-generated", "Generated with", or any `Co-Authored-By:` trailer. The commit is the user's.
2. **No personal information in messages.** Never include absolute home paths (`/Users/<name>`, `/home/<name>`), usernames, email addresses, employer/org names, hostnames, IP addresses, or secrets. Refer to files by repo-relative path only.
3. **Never push, never force, never amend published history** unless the user explicitly asks.
4. **Never use `--no-verify`** or otherwise bypass hooks.
5. **Scan before staging.** Inspect the diff for secrets (tokens, keys, passwords, `.env` values) and personal info before adding anything. If found, stop and warn the user; do not stage the offending hunk.
6. **Never `git add -A` blindly.** Stage the explicit paths for each logical group so unrelated or in-progress files aren't swept in.

## Procedure

1. **Survey the tree.**
   ```sh
   git status --short
   git diff --stat
   ```
   Note staged vs unstaged vs untracked. Read the actual diffs for anything non-obvious (`git diff`, `git diff --staged`).

2. **Scan for red flags** in the diff before doing anything else:
   - secrets / credentials / tokens / private keys / `.env` contents
   - personal info (absolute home paths, usernames, emails, org names)
   - large generated artifacts, lockfiles, or vendored dirs that shouldn't be committed
   - files that look like in-progress work the user may not want committed yet

   If anything is found, **stop and ask** rather than committing it.

3. **Group into logical chunks.** One concern per commit. Typical seams:
   - feature code vs its tests vs its docs
   - unrelated bug fixes
   - refactors vs behaviour changes
   - config/tooling vs application code
   - each independent file or subsystem when they're unrelated

4. **Propose the plan.** Present the ordered list of commits — each with the files it will include and a one-line message — and let the user confirm or adjust before you run anything. Default to smaller chunks when unsure.

5. **Commit each chunk** with explicit paths:
   ```sh
   git add <path> <path>
   git commit -m "<message>"
   ```
   Commit in dependency order (e.g. the thing being depended on first).

6. **Report** the resulting `git log --oneline -n <count>` and remind the user nothing was pushed.

## Message conventions

- **Conventional Commits**: `type(scope): summary`. Types: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `build`, `ci`, `perf`, `style`.
- **Imperative mood**, lower-case summary, no trailing period, ≤ ~72 chars on the subject line.
- Add a body (blank line, then bullets) only when the *why* isn't obvious from the subject.
- Reference issues (`Fixes #123`) only when the user provides them.
- Commit SHAs in `code` formatting when you mention them back to the user; never paste a commit message that quotes a SHA of an unrelated commit.

### Good
```
feat(auth): add refresh-token rotation
fix(parser): handle empty input without panicking
docs(readme): document the --dry-run flag
```

### Bad
```
Update files                         # vague
fix: fixed the bug (Generated by Copilot)   # tool reference
chore: cleanup /Users/jane/proj/tmp  # personal path
WIP                                  # not self-contained
```

## Notes

- If the working tree is clean, say so and stop.
- If everything is genuinely one logical change, a single commit is correct — don't split for the sake of it.
- If pre-commit hooks modify files, re-stage and re-run the commit; never bypass with `--no-verify`.
